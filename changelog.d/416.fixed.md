- **Every input CI resolves is now pinned, and one local check holds every
  place that states a pin to every other** (#416). Nothing here could make a
  committed artifact stale - the audit confirmed by execution that every
  re-derivation pair in this repo takes its input from this repo and runs on
  every pull request, which is the correct design and is unchanged. What it
  found is the same family pointing the other way: places where CI's answer
  could change **with no commit at all**, so a green run was not attributable
  to anything in the history.
- `ruff` and `pytest` moved from `pip install ruff` / `pip install -e . pytest`
  into `requirements-dev.txt`, and `build` / `twine` into
  `requirements-release.txt`. A ruff release adding a rule inside the `E`/`F`/
  `W` prefixes turned `main` red with nothing having changed, and dependabot
  could never have noticed: its `pip` ecosystem reads requirements files and
  `pyproject.toml`, never a `pip install` line inside a workflow. A file fixes
  both halves at once - the version is written down, and it is written where
  something will offer to bump it.
- `pypa/gh-action-pypi-publish@release/v1` is SHA-pinned to v1.14.2. It was the
  only moving tag in a repo where every other action carries a 40-hex commit
  SHA and a version comment, and it sits in the one job that holds an OIDC
  token, on a path that only runs at release time on an otherwise green `main`.
- **The wiki deploy builds on pull requests and deploys only from `main`.** It
  had no `pull_request` trigger at all, so `wiki/quartz.*` and
  `wiki/components/*` were compiled for the first time by the deploy itself -
  the workflow's own comment says a missing component makes the layout import
  resolve to nothing and the build fail. The `concurrency` group is now per-ref
  so a PR check cannot cancel `main`'s deploy, `node-version` is exact rather
  than the floating `22`, and `ubuntu-22.04` - a dated label GitHub retires on
  its own schedule, in the one workflow with no pre-merge check - is now
  `ubuntu-latest` like every other job. `npm ci` was left alone and the reason
  is recorded: it installs from the `package-lock.json` in the Quartz tree
  fetched at the pinned commit, which was verified rather than assumed.
- **`scripts/pin_gate.py`, and it runs inside `pytest -q`.** The lesson this
  change is named for is not "bump the pin" - it is that the fix which stuck
  was one local check holding the contract across every place that states it,
  before a push. So the gate refuses an unpinned install, a `uses:` that is not
  a SHA with a version comment, a floating `node-version`, and a runner label
  not registered with the reason it is the one chosen; and it holds
  `CONTRIBUTING.md`, `RELEASING.md` and the pull-request template to `ci.yml`,
  because a pin only does its job if the person running `ruff` before pushing
  has the same ruff. It refuses by SHAPE rather than by a list of package
  names, since a name-based rule would have let `ruff` and `pytest` through
  exactly as nothing did.
- **Three documents said `ruff check src tests` while CI ran `ruff check .`**,
  so a clean local lint said something true about two directories and read as a
  fact about the repo - the misreading that widening the CI scope was meant to
  end. `RELEASING.md` also listed three of the six hygiene steps, which made
  the other three CI-only. Both are corrected and both are now held by the
  gate.
- **`scripts/changelog_gate.py` was the one gate of five that no test ran.**
  `pytest -q` was green whether the fragments were well formed or not, and a
  badly named fragment failed after the push. It has a test file now, and the
  pin gate refuses a gate script that no test exercises, so the next one cannot
  arrive without one.
- **`uv.lock` gets the one comparison it can fail.** A repo-wide grep finds
  `uv.lock` / `uv lock` nowhere outside the file itself: nothing re-derives it
  and nothing reads it, so it cannot go red, only quietly disagree at the next
  version bump. The gate now holds its recorded version and `requires-python`
  to `pyproject.toml`. Deleting the file is the other honest answer and is left
  to the maintainer.
- Every rule is tested against a violation this repo does not contain, in
  `tests/test_pin_gate.py`. A gate asserted only against the tree it guards
  passes because the tree is clean rather than because the gate works, and it
  stops working silently the day somebody edits it.
