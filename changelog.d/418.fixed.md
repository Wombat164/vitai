- **`overlapping_instrument_problems` is dispatched, five contracts after it
  was written** (#418). Two instruments claiming one origin over overlapping
  intervals means a reading falls into both, and the register cannot say which
  physical thing produced it. The check was written for #311, documented,
  and exercised in five places by `tests/test_instruments.py` - and
  `api.validate` never called it. A repo-wide grep found it in the module that
  defines it and the file that tests it, nowhere else. So it passed its own
  tests, reported no problems, and had never once run over anybody's record;
  from outside, a validator that is never dispatched is indistinguishable from
  one that keeps finding nothing.
- **It runs over the merged device stream, not just `instruments.jsonl`**
  (#105). Two device files each registering the same origin is exactly the
  collision a union merge makes possible, and it is the case reading one file
  would miss.
- **An advisory, not a problem** (#38). Both lines are legal, already on disk,
  and an append-only record cannot edit either; the repair is to APPEND a
  `supersedes` correction, which the check already reads, so a corrected
  register goes quiet. The argument the other way is recorded beside the call
  rather than dropped: `policy.instrument` returns the first matching row, so
  inside an overlap it attributes a reading by FILE POSITION and a sort or a
  device merge can change the answer silently. That is a wrong answer rather
  than a cosmetic one, and the condition for escalating it to a problem is
  written down where the decision is.
- **Nothing turned red.** Dispatching it produces zero advisories across every
  record this repo ships - the demo and all sixteen persona fixtures - and
  that number is now asserted in the suite rather than stated here, so it can
  stop being true out loud.
- **The class, not just the instance: `tests/test_validator_dispatch.py`.**
  Every public check in `schema` that returns a report must either be observed
  running during `Vitai.validate()` or be named in an allowlist with the reason
  it is not. MEASURED BY EXECUTION, never by name-appearance - the obvious
  version reads `api.py` and asks whether a function's name occurs inside
  `validate`, which is exactly the defect #412 was filed for one layer up,
  where the population register counted a field's WRITER as a reader. The
  allowlist fails closed: a new check that is neither dispatched nor
  registered fails the suite. Two entries today - `removal_problems` and
  `aliases_for` - and both `removal_problems` and `exercises.registry_problems`
  / `exercises.validate_fixtures` now say in their own docstrings that the
  suite is their dispatcher and why, which is what stops the next reader
  re-deriving it.
- The census carries a control on itself. Its first draft rebuilt the

  return annotation, the set came back empty, and the gate passed on nothing -
  this file's own subject, in this file. `test_the_measurement_can_fail` is
