- `scripts/vacuity_gate.py`: a test that runs, passes and executes none of its
  own assertions is now a red build. #424 found three by hand and every one had
  been green for months, including a G69 SAFETY guard keyed to a string the
  rollup had stopped emitting - because a check reports "pass" for two different
  states, the property held and the property was never looked at, and nothing
  distinguished them.
- A REGISTER, not a bare red build, which is the shape #424 argued for and the
  objection it raised itself: a zero-iteration loop is sometimes correct. So
  `VACUOUS` is an allowlist that fails closed - an unregistered finding fails,
  a registered one must commit to A DECISION or A GAP, and an entry that gains
  an executed assertion has to leave. It ships EMPTY, because #431 repaired the
  four this issue found.
- It fails closed on its own input too. Handed no coverage data it exits 1
  rather than 0, and so does data collected with the wrong `--source` that
  measured no test file: a gate that passes when it was given nothing to
  measure is the decorative CI step this gate exists to find.
- The cost is a coverage run, in a `vacuity` job of its own. Putting it in
  `tests` would make the four-leg matrix pay for one answer four times, and it
  is the one gate `pytest -q` cannot run over this repo - its input is the
  completed run it would be part of. Its rule is therefore exercised by
  `tests/test_vacuity_gate.py` against inputs this repo does not contain, which
  is the same argument the gate makes about the tests it reports.
- Scoped, and the limits are stated rather than discovered: a test with no
  inline `assert` of its own is not reported, because plenty here assert
  through a helper and a gate crying wolf on its first run is a gate nobody
  keeps; a test whose body never ran is not reported, because a skip says
  nothing about its assertions; and `src/` is not measured, which is a
  different question with a different answer.
