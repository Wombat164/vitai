- Four tests ran, passed, and executed none of their own assertions. Each is
  repaired so its case occurs, and each now asserts that it examined something -
  because a check whose non-vacuity is hoped for is a check that can go quiet
  again without a single build going red.
- The scale check read `units(ds, f).get("scale")`, and no entry in the units
  registry uses the key `scale`; the keys in use are `ucum`, `label`, `ordinal`,
  `scale_of`, `unit_of`, `unit_in`, `machine_scoped` and `unstated`. The slug is
  a fact about the ROW rather than the column - two athletes' `rpe` sit on
  different Borg scales in one corpus - so `scale_of` names the field that
  carries it, and the check now reads the 690 slugs the corpus actually writes.
  The scale-bearing fields are derived from `scale_of` rather than from the
  `_scale` suffix, since a suffix is the naming convention this module exists to
  stop trusting.
- The G69 rate guard was keyed to `"kg/week" in text` and the rollup stopped
  emitting that string on its fixture, which renders `**Rate:** losing over 13
  days, a thin sample (no phase targets configured)`. This is a SAFETY property -
  the line once showed `+1.10 kg/week` to an athlete who had lost 1.5 kg,
  because positive means losing - and it was unguarded while the suite reported
  it covered. It now reads the line the rollup emits and asks what G69 asks: a
  signed quantity with no direction word fails, an explicit refusal owes none.
  Two fixtures, because the directioned shape and the refusing shape prove
  nothing about each other.
- `test_a_refusal_carries_no_numerator` asserted only inside `if row["value"] is
  None`, and its three-row fixture produced no such row. A refusal needs a
  metric that is scored and has no input, so the fixture now configures a phase
  and leaves a week without a weigh-in; `weight_rate` refuses with `no_data` /
  `no_input`. A companion checks the same property over `yasmin`, whose rows
  nobody wrote for this test.
- The retirement scan was the honest vacuous case - every `KEY_REMOVAL` entry is
  unscheduled, so the loop body never ran - and it was the one check in that
  file without a control. The rule is now a pure function with one, exercised
  against a scheduled removal this repo does not contain. Nothing pins which
  entries are scheduled: that file's own rule is that scheduling one must not
  fail a test whose name says nothing about scheduling.
