- An absent field is no longer ambiguous at the install boundary. The core
  install is dependency-free and some work ships as an optional extra, so a
  row enriched by the extra carries fields a core install cannot produce, and
  a consumer meeting an absence could not tell whether the value was not
  measured or the writer could not measure it. `semantics/builds.toml` records
  what each released build can emit, and `can_emit(field, build)` and
  `absence(field, build)` answer from it - on the API, the CLI
  (`vitai can-emit`) and the agent surface.
- It is engine data keyed on a BUILD, not on an install, because contract 34
  refused an install identifier deliberately: a stable per-install id is a
  tracking key. It carries history rather than describing only the build in
  front of you, since an absence written by an older build is the case this
  exists for. It is a separate dataset from an instrument's capability, and
  shares none of that dating machinery - a build's abilities are fixed at
  release, so the axis is the version rather than the calendar.
- A build the registry does not cover resolves to `unknown`, and most
  historical rows do. Nothing on an ordinary row says which build wrote it, so
  `absence` requires the writing build to be passed and answers `unknown`
  rather than defaulting to the install doing the reading. That is the honest
  answer rather than a gap papered over: the record cannot tell you which
  reading is right, said out loud instead of left to be inferred.
- No extra is declared yet, because the route extra is not built. A build
  listed as shipping none is a positive statement that it emits the core and
  nothing beyond it, which is what makes `not_measured` sayable at all.
