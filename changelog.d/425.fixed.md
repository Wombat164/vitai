- **A correction can now be recognised before it is appended** (#425). Nothing
  public could ask what a write would do until the write did it, and the private
  guard that looked like the answer gave the wrong one on legal input. It
  compares `recorded_at`, a pending row may not carry `recorded_at` - "the one
  clock in the record that cannot be authored" - and `merge` sorts absent before
  present by design, so every correction in an unstamped batch was reported as
  sorting ahead of its target and refused. The refusal was manufactured by the
  question rather than read off the record, and it broke the ordinary case: a
  day exported at lunchtime and completed after dinner, restated with
  `supersedes`.
- `pending_problems(data_dir, name, pending, now=, device=)` returns the
  sentences `append_many` would raise with, over the same rows, before the
  write. The stamp is modelled by DOING it - `_prepared`, split out of
  `append_many`, is the same assignment over the same file - so asking gives the
  answer the write gives rather than an estimate of it.
- The guard the peer case exists for still fires. High water comes from THIS
  device's file alone (#105), so a row a peer stamped ahead is still ahead of
  the modelled stamp and the correction is refused exactly as the write refuses
  it. Taking high water from the merged record instead would have silenced it,
  which is #391's view-dependence arriving from the other side; a test holds
  both directions, including that a written row reads the same on every machine
  after sync.
- `_corrections_that_would_not_apply` now REFUSES to answer about an unstamped
  row rather than answering wrongly, and names `pending_problems` in the
  refusal. A new public name in front of the old answer would have left the trap
  for the next caller.
