- **A retired key now has to say when it stops being carried** (#126, G89 part
  four). `KEY_RETIREMENT` recorded the generation at which a key stopped being
  expected and nothing recorded when it leaves, so every adopter inherited the
  field, its validation branch and the reader machinery behind it for as long
  as the engine exists. `KEY_REMOVAL` is the missing half: each of the four
  retired keys states either a generation or `None` with the precondition that
  would let one be named, and `schema.removal_problems` reports a retirement
  that states nothing, a decision naming a key that is not retired, a removal
  scheduled at or before its own retirement, and - the one this is for - a
  generation that has passed while the key is still in `KEYS`, which turns the
  register into a promise nothing kept.
- All four are unscheduled today and that is a recorded decision rather than a
  blank. Removing a key from `KEYS` makes every line carrying it fail with an
  unknown-field error, and this repo's own corpus still writes three of the
  four; a test asserts that a key the corpus still writes cannot be scheduled,
  so the precondition is checked rather than described. The two terminal
  retirements carry a different argument from the two forward-mapped ones and
  the register keeps them apart: with no successor, removal makes a value
  unreadable rather than relocating it, so migration cannot be what an end is
  conditioned on.
- **A legacy pain line is now pinned all the way to the verdict.**
  `compute_verdicts` reads `pain` and nothing else, on the grounds that rows
  arriving have already been mapped - which is a property of every call site
  rather than of the function, and nothing checked it. The existing legacy test
  resolves its rows by hand first, so it would have stayed green if
  `Vitai.verdicts()` began passing raw ones. It would not have raised or
  warned either: a legacy line has no `pain`, so it would drop out of the pain
  gate silently and a record whose only pain lines predate the generalisation
  would report no pain at all while validating cleanly.
